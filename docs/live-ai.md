# Live AI inspection

This source adds a disabled-by-default Groq model endpoint and an optional panel in a signed-in saved-project workspace. It needs a separately reviewed database migration and endpoint deployment, server secrets and live acceptance before it works. The private candidate tests use fake providers and a local PostgreSQL WASM fixture. They do not prove live Groq, cloud permissions, overlapping SQL transactions, cross-device persistence, GPU or Quest behavior.

The panel makes no AI request on mount. Check availability, explicitly save project consent, then ask a question about a selected saved object. The server verifies the caller with Auth `getUser`, reads context through that caller's JWT, and reserves the existing service-only database budget before each provider dispatch. The new function uses `verify_jwt=false` because its own remote caller verification is mandatory; this does not grant anonymous project access. The service credential is used only for the budget RPC and is never sent to the browser or Groq.

Groq receives the question, saved project scope, frame/object IDs, and bounded tool measurements. Raw point clouds, original ZIPs, storage URLs, class text and unrelated project metadata are excluded. Five custom tools can list issues, inspect support, compare tracks, measure a fit and focus an existing object. There is no network, shell, edit, approve, save, upload or delete tool. The final answer is a constrained assessment citing completed evidence; numbers shown in the panel come directly from the validated measurement worker. A fit requires an explicit **Preview measured fit** click on the matching frame/object. The existing **Approve and save** action remains a separate human action.

Each turn allows at most three model calls and eight tool calls. Existing database limits are 30 member turns, three demo turns, and 300 provider calls globally per UTC day. Reservations are not refunded automatically on failures. A replay never dispatches again; there are no provider retries. Response byte bounds, timeouts, strict schemas, saved revision/source binding and cancellation guard every stage. Revoke consent to block subsequent dispatches; an already sent provider request cannot be recalled. Changing saved state or signing out cancels the local turn and clears its proposal. Manual review remains available when AI is disabled, unavailable or over budget.

Server-only variables: `AI_ENABLED=false`, `GROQ_API_KEY`, `GROQ_MODEL=openai/gpt-oss-20b`, plus the existing Supabase public/server key and `ALLOWED_ORIGIN` configuration. Never place the model or server key in a `VITE_` variable, source, report or chat. Build/verify the generated endpoint with `node scripts/build-agent.mjs --write` / `--verify`. Apply `202611060001_ai_context.sql` only after a separately reviewed cloud preflight. It adds the caller-owned consent/context function and changes exactly one deterministic stale budget signal from `40001` to `PT409`, preserving the budget function owner, ACL and all other body text. Do not rerun an already applied migration or bypass its guards.

Remaining live acceptance: deployment source provenance, real-model valid/invalid tool turns, consent enable/revoke, ownership and stale revision handling, budget/replay/failure handling, no auto-edit proof, second-account API security and device/session cleanup. Existing revision-seven synthetic project must remain preserved unless a later exact test explicitly authorizes a bounded change.


## Response validation and failed-test recovery

Tool stages omit `response_format` entirely because Groq rejects JSON mode combined with tool/function calling. Tool arguments and any early final answer still pass the existing strict server validators. The final-only stage sends no tool definitions, tool choice, parallel-tool option or tool-role transcript; it uses a strict assessment schema with evidence IDs limited to completed calls. The server still validates the assessment enum, nonempty bounded citations, uniqueness and actual completed evidence. Truncation, malformed replies and unknown references remain errors; no automatic provider retry or label edit is added. Existing limits remain three model requests, eight tools and 700 completion tokens per request.

A rejected model reply returns the existing ai_response code and one fixed diagnostic reason, such as finish-length, final-json, final-schema or final-evidence. No model prose, reasoning, credential, measurement body or upstream error is added to the diagnostic. Manual review stays available. The earlier Step146 reply was not retained; its precise rejection reason cannot be reconstructed from the old generic error.

The recovery harness binds its cached transport to the current report object. Its counters and failed-step diagnostic therefore survive a restored workspace receipt without resetting the independent dispatch/replay limits. The two stopped Step146 folders and reports remain frozen evidence. This candidate has no live acceptance claim.
