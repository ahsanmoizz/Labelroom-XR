What we are building

LabelRoom XR is a hands-first review room for people who check existing 3D object labels. They open a real point-cloud scan, see the boxes that describe objects, inspect suspicious boxes in depth, approve a correction, and export labels that their existing data pipeline can use.

A point cloud is a scan made of many measured dots. A label is a named 3D box around an object, such as a car. We are correcting that label data. We are not training a vision model in the headset.

Final outcome: a reviewer can use their own supported data, save a private project, reopen it, finish a review without controllers, and get a corrected dataset plus a clear history of every decision. That complete loop is the product.

Who needs it, what goes wrong, and the value

QuestionOur exact answer
Primary userA 3D dataset reviewer in a small ML, robotics or mapping team. The user already has scans and bounding-box labels. We are not targeting general headset owners.
ProblemA box can be shifted, too large, duplicated or inconsistent across frames. Reviewing depth and occlusion on a flat screen requires repeated rotations and views. Bad labels can be passed downstream if the reviewer misses them.
Useful changeBring a short troublesome clip into a seated spatial workspace. The assistant measures candidates, focuses the object, and offers a constrained proposal. The reviewer sees the evidence and stays responsible for the edit.
What is savedCorrected OpenLABEL geometry, preserved IDs/classes/metadata, unchanged scan points, input/output hashes and a before/after decision record. Another developer can reimport and verify the result.
Repeat useA reviewer returns for the next difficult clip, or resumes an unfinished private project. No points, streaks or artificial game loop are required.
Commercial value hypothesisLess effort on difficult review tasks and fewer missed geometry errors. This must be measured; there is no proven customer demand, revenue or speed advantage yet.

Research based on interviews with 3D annotation practitioners identified many distinct error types. That supports the existence of the problem, not demand for our particular app. Annotation-error research ↗

AI has a narrow, real job

The assistant is a tool user for 3D review, not a generic chat window. For “inspect this suspicious box,” it can ask for point support, compare the same object across frames, focus it in the scene, and request a bounded fit proposal. Its recommendation includes measured numbers. It cannot write to the database, delete an arbitrary object, or approve its own suggestion.

CheckWhat it can tell usWhat it cannot prove
Fewer than 5 points inside a boxThis box has little visible scan support. It deserves inspection.That the label is wrong. Occlusion and sparse scans are common.
Two same-class boxes with ≥0.90 overlapThese may describe the same object twice.Which object ID should be kept. The reviewer must confirm the pair.
Dimension changes >20% in adjacent frames ≤1s apartThe same track has an abrupt size change.That the earlier frame is the correct reference.
Bounded fit proposalA geometrically supported candidate within strict movement/size/yaw limits.True object size behind an occlusion, class correctness or improved model accuracy.

Removing the cloud model leaves import, geometry checks, manual spatial review, persistence, undo and export. The core work remains useful. Live AI is still required for our planned agentic submission claim.

Why use VR — and what we must prove

Depth, box orientation and the space behind a partly hidden object are directly relevant to this task. A reviewer can inspect a small 3D scene while keeping measurements and controls nearby. The workspace can stay seated and does not depend on scanning the user’s actual room.

Existing VR point-cloud annotation research reported benefits in a limited plant-annotation study, using controllers. It does not prove hands-only road-scene review is faster. Other research found bare-hand ray selection slower or less precise than controllers in some tasks. Our precision buttons and real Quest testing address that risk. Existing VR annotation study ↗ · Hand/controller study ↗

Before the final pitch, three actual data/ML reviewers must complete matched desktop and VR tasks. We report raw time, mistakes and comfort. If VR has no observed benefit, we do not claim that it improves productivity. We fix the interaction first or describe the evidence honestly.

Competition and winning rationale

There is no defensible winning percentage. Our reason to choose this direction is that it can show a useful end-to-end tool, spatial work that matters to the task, hands-first interaction and a real agent using measurable tools. Those qualities can support the four equally weighted criteria: innovation, experience design, implementation and polish. Official judging criteria ↗

The scope is fixed

IncludedExcluded until after this competition
Short existing labelled real scans; geometry review; private projects; live assistant; exact exportNo vision-model training, new object detection, class prediction or missing-object discovery.
PCD + our supported OpenLABEL subset; 10 frames maximumNo LAS/LAZ/PLY, general OpenLABEL compatibility, arbitrary pickle uploads or automatic scan registration.
Hands, desktop keyboard/mouse fallback, seated tabletop reviewNo voice, eye tracking, live room scanning, hardware sensors, physics or game mechanics.
One reviewer owns a project; optimistic version conflictsNo multiplayer, team roles, live collaboration, comments, billing or enterprise SSO.
Production handling for this defined small workloadNo claim that this is a replacement for a mature annotation platform or safety-certified autonomous driving tooling.

Prerequisites that cannot be hidden

If data rights, headset access or basic agent access are unavailable after the early gate, stop this sealed build and make an explicit decision. Do not keep coding and replace proof with a polished animation. No document can guarantee that all future problems or winning risk disappear.
